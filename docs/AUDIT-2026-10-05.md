## What Nova Shop is

Nova Shop is a Telegram-native commerce platform combining:

~~~text
Telegram Bot
   +
Telegram Mini App
   +
Payload CMS/admin
   +
transactional bot database
   +
fiat / Stars / CryptoBot / blockchain payment rails
   +
catalog/export/sync tooling
   +
optional SaaS tenant layer
~~~

It already covers real commerce features: catalog, cart, checkout, inventory, digital/physical fulfillment, payment recovery, promos, referrals, support, admin operations, and Mini App checkout.

## Highest-priority findings

### H1 — Telegram digital-goods payment classification

The repository presents crypto/card/CryptoBot/TON alongside digital goods. Telegram's current digital-goods payment rules require Telegram Stars for digital goods/services sold inside Telegram.

**Required:** classify products/orders before payment-method generation and enforce the permitted rail set server-side.

Reference: https://core.telegram.org/bots/payments-stars

### H2 — Payload Orders write access is too broad

Any logged-in user can update Orders, including financial and settlement fields.

Payload supports field-level access control.

**Required:** reserve payment amount, payment method, financial status, raw provider payload and settlement data for system/admin roles; give staff only the operational fields they need.

Reference: https://payloadcms.com/docs/access-control/fields

### H3 — Payload Products write/delete access is too broad

Any authenticated user can create/update/delete catalog records.

**Required:** enforce role-specific permissions and reserve destructive operations for admins.

### H4 — Payload Users role boundary is incomplete

The users collection exposes API keys and a role field without a strong explicit policy for role changes and service identities.

**Required:** make role changes admin-only and distinguish human users from integration/service users.

### H5 — Chain payment identity is too generic

The payments table deduplicates provider + external_id. That is insufficient as the only identity for some chain events; an EVM transaction may contain multiple relevant token Transfer logs.

**Required:** store a normalized chain event identity containing network, asset/contract, transaction hash/signature and event/output index where the chain model requires it.

### H6 — Fulfillment is not one database transaction

Payment recording, stock/digital-key claiming, payment status, and order status occur across separate operations.

**Required:** make the critical fulfillment claim transactional, or use a durable job/outbox with an idempotency key and explicit compensation/retry semantics.

### H7 — Runtime locks are process-local

The per-user placement locks, in-memory rate limits and asyncio claim lock do not coordinate across multiple bot instances.

**Required:** database-backed conditional writes must remain the final guard; move coordination to a shared DB/queue/distributed lock for horizontal scaling.

### H8 — Bot migrations are ad hoc

bot/database.py uses startup ALTER TABLE statements wrapped in broad exception handlers.

**Required:** use numbered migrations with explicit schema versioning and migration tests.

### H9 — Telegram webhook secret is not configured

The current app builds a webhook URL but does not configure/verify secret_token.

**Required:** verify the Telegram secret header before accepting webhook updates.

Reference: https://core.telegram.org/bots/api#setwebhook

### H10 — Mini App HTTP authentication is a future-only helper

webapp_auth.py exists, but no browser HTTP API is currently built around it.

**Required:** keep the helper tested and make validated initData mandatory before adding privileged HTTP endpoints. Never trust initDataUnsafe.

Reference: https://core.telegram.org/bots/webapps

## Medium findings

### M1 — aiogram 2.25.2 is an older architecture choice

aiogram 3.x provides a substantially different and more modular architecture. Migration is worthwhile but should be a dedicated project instead of mixing with payment changes.

Reference: https://docs.aiogram.dev/en/dev-3.x/migration_2_to_3.html

### M2 — Python version mismatch

README says Python 3.12; bot Dockerfile uses Python 3.11.

**Required:** choose one runtime and use it in local docs, CI and container images. Python 3.12 is the clearer target based on the repository's stated development policy.

### M3 — Admin package manager mismatch

admin/package.json includes a package-lock.json but scripts/tests call pnpm while root docs use npm.

**Required:** standardize on npm now because the repository already tracks package-lock.json, then use npm ci in CI.

### M4 — Mini App monolith

miniapp/app.js is roughly 74 KB and styles.css roughly 38 KB, with generated dist output on top.

**Required:** split source by state, catalog, cart, checkout, payment, Telegram bridge and UI primitives.

### M5 — Dual databases

Bot SQLite and Payload SQLite are separate systems.

**Required:** either move toward shared Postgres for the business data or introduce a durable outbox/event boundary and make the split explicit.

Reference: https://payloadcms.com/docs/database/postgres

### M6 — Best-effort CMS mirroring

payload_hooks.py intentionally drops CMS failures so checkout remains independent.

**Required:** keep the financial ledger in the bot database and make CMS synchronization durable/retryable.

### M7 — TON Connect manifest/policy URLs

The manifest currently points terms/privacy to the Telegram bot URL.

**Required:** publish stable HTTPS legal pages and set the manifest app URL to the canonical Mini App origin.

### M8 — Large binary archive in source tree

nova-shop-complete.zip is tracked in the repository.

**Required:** move release archives to GitHub Releases rather than maintaining a second distribution artifact in source.

### M9 — In-memory rate limits

Rate limiting resets on process restart and is not shared across instances.

### M10 — Payment module concentration

crypto_payments.py contains chain config, quote providers, wallet derivation, CryptoBot API and payment math.

**Required:** split chain adapters, quote service, wallet adapter, provider clients, payment matcher and reconciliation worker.

## Low / quality findings

- admin retains starter/template frontend content;
- handlers/common.py and handlers/texts.py are very large;
- legal copy belongs in a dedicated policy module;
- tools include both bootstrap and routine sync logic and should be separated;
- deployment docs reference deployment files not visible in the main tree;
- Mini App source and generated assets need an explicit generated-file policy.

## Recommended order

P0:
1. Enforce Telegram payment-rail classification.
2. Restrict Payload access at collection and field level.
3. Strengthen chain-native payment identity.
4. Make fulfillment durable/transactional.
5. Secure webhook ingress.
6. Add versioned bot migrations.

P1:
1. Standardize npm and Python 3.12.
2. Add CI/SAST/secret/dependency scanning.
3. Split crypto/payment providers.
4. Add durable outbox/reconciliation.
5. Harden TON Connect verification and manifest URLs.

P2:
1. Split Mini App modules.
2. Move business state toward Postgres where scale requires it.
3. Migrate aiogram 2 to 3.
4. Move ZIP artifacts to releases.
5. Remove legacy starter/duplicate code.

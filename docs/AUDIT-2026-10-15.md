# Nova Shop Deep Audit — 2026-10-15 (first pass + fix programme)

## Scope

Repository: Pr3eve6ti2o/nova-shop-assets, branch
`refactor/nova-shop-professional` at `5ed0f36` when the audit began.

Method: a 318-chunk sweep of the bot codebase in 22 sections, run on
external Opus models against the branch's own docs and README first.
The provider pools collapsed mid-run: the first pass banked **25 of
318 chunks** (a further 21 results were discarded as off-brief
fallback output). The remaining 293 chunks are still pending a
mop-up run, so this document covers the banked scope only — it is
not a completed full audit.

Every banked finding was then **re-verified against the current code
before any change**. Roughly half of the prose findings were refuted
by the code as already handled; only confirmed defects were fixed.
Fixes landed as eight commits (one per part), each followed by the
full unit suite and a verified test-bot deployment.

This is an engineering review, not a penetration test, legal opinion,
or production custody certification.

## Highest-priority findings (confirmed and fixed)

### H1 — EVM deposit addresses were issued to multiple orders (04-crypto, `8dad87d`)

Every EVM chain shares one xpub (`XPUB_ETH`) and one BIP44 derivation
path, but the derivation index counters were keyed per chain name.
The same address was therefore handed to the first order on each EVM
chain (the live test database showed index 1 issued on four chains) —
payments to it could not be attributed to a single order. Counters are
now scoped to the xpub (the derivation domain); migration **m016**
seeds each scoped counter from the maximum legacy per-chain value so
no already-issued index can recur.

In the same part: manual crypto confirmation read a column that does
not exist (`amount_cents` on `crypto_deposits`), so every manual
confirm was blocked as underpaid; the gate now compares observed vs
expected units under the watcher's tolerance, and finalisation runs
before the deposit is marked paid, with its result honoured. Deposit
rejects now refuse deposits with funds observed on-chain, the
chain-disable confirmation arm actually stores state, the derivation
daemon's teardown moved inside its lock, daemon spawning no longer
inherits the bot's secrets, private extended keys are refused,
derived addresses are shape-checked, and the watcher resolves chain
metadata via `active_chains()` (it KeyErrored on testnet chains).

### H2 — Two admins could fulfil the same stuck order twice (06-admin, `f9a5a06`)

The stuck-order recovery path checked claim staleness with a plain
read and then fulfilled: two admins clicking together both passed and
both fulfilled — double licence keys, double stock decrement, double
referral credit. The path now steals the stale claim atomically
(`steal_stale_order_claim`, the compare-and-set the crypto watcher
already used); only the winner fulfils. The same path called
`logger.warning` in a module that never defined a logger, so the
recovery itself crashed with `NameError`; fixed, and fulfilment
exceptions now surface as an admin alert instead of a silent hang.

Also in this part: concurrent cancels could release a promo twice
(the transition is now won with a compare-and-set before release);
cancelling a **paid** order writes an `order_cancel_paid` audit entry
and alerts admins that a refund is owed; "Mark refunded" recorded and
announced the full order total even after partial refunds and crashed
unhandled when the order row was missing — it now records
paid-minus-already-refunded from the refunds ledger; the
balance-refund path records the amount actually credited; the
maintenance toggle accepts only exact `1`/`0` payloads (any other
value previously meant OFF).

### H3 — Support inbox: stored HTML injection and cross-customer replies (07-users, `6c3343d`)

The admin inbox rendered raw customer ticket bodies (and names) into
an HTML message — stored injection aimed at the highest-privilege
reader, and one malformed tag silently bricked the ticket view. It is
now escaped, as the customer-side view already was. Admin replies
could also reach or be filed under the wrong customer three ways:
the quick-reply button merged FSM data and left a stale ticket
binding; force-reply prompts were not bound to a conversation, so
answering a stale prompt delivered the text to whoever the state
currently targeted (prompts are now bound by message id and stale
replies are refused); and closing a ticket left the reply flow armed,
so the admin's next message went to the customer. All three are
closed. Purchase-history pages beyond page 1 were unreachable (no
navigation buttons), which hid older licence keys from customers with
more than ten orders; Newer/Older navigation was added.

### H4 — Expired-credit sweep counted money it never debited (08-db, `57f6b1f`)

`credit_sweep_expired` zeroed an expired lot with a compare-and-set
(correct), then added the amount to its forfeited total
unconditionally — but the balance debit behind its
`balance >= amount` guard legitimately affects zero rows when the
lot's backing was already spent or is NULL, so the sweep reported
forfeitures that never happened. The debit's rowcount is now checked;
only money actually taken is counted.

### H5 — Checkout state resurrection on change-payment (03-checkout, `f9c18ad`)

Changing the payment method on a pending order restored the cancelled
order's delivery details and payment keys into live FSM state — with
an old delivery order this could re-enable the delivery-details/COD
path that is intentionally switched off. The handler now mirrors
`start_checkout`'s state hygiene, re-validates restored items with
full availability (not just `is_active`), and names any items it
could not restore.

### H6 — Remaining parts (01-core `c5272c4`, 02-shop `9ce9c64`, 05-rent `5f1ac01`)

- Shutdown: a previously-crashed worker's exception could abort all
  remaining cleanup; background tasks (watcher, outbox, campaigns) ran
  unsupervised and died silently — they now log crashes via a
  done-callback supervisor.
- Shop/cart: a systemic double-answer defect (Telegram accepts one
  callback answer; the second, usually the error alert, was rejected)
  in the category/product handlers and the dropped-items toast; the
  quantity stepper treated any unrecognised delta as −1; photo
  captions lost HTML parse mode; cart navigation could leave a user
  trapped in the promo-code state.
- Rent: the callback's provider string reached the billing API (and
  the HTML confirmation text) unvalidated — it is now allowlisted, the
  plan is re-validated at confirm, a per-user lock stops double
  submits, "Charged" renders only for a genuinely ACTIVE balance
  charge, and prices format from integer cents. The unwired
  `saas/tenants.py` scaffold carried a stale $4.99/$49.99 price table;
  the constants now mirror the standing $8.99/$89.99 plan so a future
  wiring cannot mint them by accident.

## Refuted on re-verification (no change made)

The order-detail IDOR claim (ownership is the first check in the
renderer); the cancel-claim atomicity claim (`set_order_status` with
`only_if_status` is a single conditional UPDATE under the claim
lock); cancel-versus-late-payment money loss (every rail records the
payment first, then quarantines or alerts for manual refund); refund
double-spend (conditional UPDATE plus ledger insert in one
transaction); referral double-credit (atomic claim); the rent-billing
P0 cluster (the module is unwired scaffold — live billing is owned by
the control plane); promo double-release (claim-lock-serialised and
conditional); ticket-close IDOR (ownership is in the SQL `WHERE`);
maintenance-permission fail-open (a literal non-zero constant).

## Flagged, not fixed — since closed (2026-10-16, `f111161`)

Expired credit lots remained spendable between their expiry time and
the next sweep run, because `deduct_balance` debited the plain balance
and consumed only non-expired lots. The sweep's accounting was honest
(H4), but closing the spend window meant enforcing expiry inside the
debit path itself — a money-code change that needed an explicit
decision. The owner gave that decision on 2026-10-16: `deduct_balance`
now caps every debit at the spendable balance (plain balance minus
the remainders of lots already expired), computed inside the claim
lock and enforced by the same conditional UPDATE, so expired credit
is unspendable from the moment it expires. This covers checkout
balance payment, manual-order balance charges and admin debits
(`adjust_balance` delegates to `deduct_balance`). Regression test:
`test_expired_lot_unspendable_before_sweep`. Suites after the fix:
unit 105/105, pricing green; test bot redeployed and verified live
on `f111161`.
